# Blogville Constitution

블로그들이 모여 사는 마을. 글을 쓰고 꾸미면서 내 캐릭터와 블로그를 키워 가는 게임형 블로그 서비스.

## Core Principles

### I. 글쓰기가 먼저, 게임은 돕는 역할 (Writing First)

- 모든 기능은 "글을 꾸준히 쓰게 돕는가"로 판단한다. 게임 요소(레벨, 코인, 아이템, 동물, 광장)는
  글쓰기와 꾸미기를 돕는 보상이어야 하며, 글쓰기·읽기·교류를 막거나 그보다 앞서면 안 된다.
- 코인은 활동으로만 얻는다. 유료 결제는 하지 않는다.
- 범위 밖: 실시간 멀티플레이, 유료 결제, 네이티브 모바일 앱.

**이유**: Tistory 같은 블로그는 도구로는 훌륭하지만 꾸준히 쓰게 만드는 동기가 약하다. Blogville의
존재 이유는 그 동기를 게임 보상으로 채우는 것이다.

### II. 요구사항 ID는 바꾸지 않는다 (Stable Requirement IDs)

- 요구사항은 `영역-번호`(AUTH, BLOG, POST, SOC, GAME, SHOP, TOWN, NF) ID를 가진다.
- ID는 한 번 정하면 바꾸지 않는다. 없앤 요구사항은 지우지 않고 상태를 `❌ 제외`로 바꾼다.
- 모든 spec, plan, task, 코드 리뷰는 원본 요구사항 ID를 그대로 가리킨다.
- 원본은 `docs/01-requirements.md`다. spec과 원본이 다르면 원본의 최신 결정(변경 이력, 날짜가 붙은
  "변경 결정")이 이긴다. 원본을 고치면 변경 이력에 한 줄을 더한다.

**이유**: 문서, 코드, 이슈가 ID로 서로를 가리키므로 ID가 바뀌면 추적이 끊긴다.

### III. 확인할 수 있는 수용 기준 (Testable Acceptance)

- 모든 요구사항은 "~하면 ~된다" 형태의 수용 기준을 가지며, 그대로 테스트 시나리오로 쓴다.
- 모호한 표현을 쓰지 않는다. "빠르게" 대신 "1초 안에", "잘 보인다" 대신 "375px에서 가로 스크롤이 없다".
- 사용자에게 보여줄 문구(오류 문구 포함)는 spec에 그대로 적는다. 오류 문구는 한국어로, 무엇을 고치면
  되는지 알려준다.
- 모르는 것은 지어내지 않고 열린 질문(`[NEEDS CLARIFICATION]`)에 적는다. 정해지면 본문으로 옮긴다.
- 한 요구사항에는 한 가지 기능만 담는다.

**이유**: 화면 담당과 서버 담당이 같은 기준으로 "완성"을 판단해야 한다.

### IV. 권한과 검증은 서버에서 (Server-Side Authority) — NON-NEGOTIABLE

- 글 수정·삭제, 장착, 구매, 보상 지급, 관리자 기능의 권한 검사는 모두 서버에서 한다. 화면에서 숨기는
  것은 편의일 뿐 보안이 아니다.
- 사용자 입력은 서버에서 다시 검증한다. 가입 요청 등으로 권한(role)을 바꿀 수 없어야 한다.
- 사용자가 쓴 HTML은 저장할 때 허용 목록으로 정화한다. 첨부는 우리 저장소 주소만 허용한다.
- DB 쿼리는 값 바인딩으로만 만든다. 입력값을 쿼리 문자열에 이어 붙이지 않는다.
- 비밀값(DB 접속 정보, 로그인 비밀키, 소셜 Client Secret, 관리자 비밀번호)은 서버 환경 변수에만 둔다.

**이유**: 코인과 아이템이 걸린 서비스는 조작 시도가 생긴다. 클라이언트는 믿을 수 없다.

### V. 코인·경험치는 원장으로 (Ledger Integrity) — NON-NEGOTIABLE

- 코인·경험치·레벨은 따로 저장하지 않고 원장(ledger) 합계로 계산한다.
- 코인 지급·차감, 구매처럼 여러 단계가 함께 바뀌는 처리는 하나의 트랜잭션으로 한다. 중간에 실패하면
  전부 취소된다.
- "하루 한 번", "한 글에 공감 한 번", "보유한 아이템만 장착" 같은 규칙은 앱 코드뿐 아니라 DB 제약조건으로도
  막는다. 동시에 두 번 요청해도 한 번만 처리된다.
- DB 구조 변경은 마이그레이션 파일로만 한다.

**이유**: 잔액이 원장과 어긋나면 게임 보상 전체를 믿을 수 없게 된다.

### VI. 모바일에서도 쓸 수 있다 (Responsive by Default)

- 모든 화면은 375px 너비와 PC에서 가로 스크롤 없이 쓸 수 있어야 한다.
- 버튼과 링크의 누르는 영역은 최소 44×44px이고, 버튼 글자가 두 줄로 쪼개지지 않는다.
- 광장(게임 화면)은 마우스와 터치로 조작할 수 있어야 한다.

**이유**: 블로그 독자 상당수는 휴대폰으로 들어온다. 모바일 앱은 만들지 않으므로 반응형 웹이 유일한 길이다.

### VII. 단순하게, 최소한의 정보만 (Simplicity & Minimal Data)

- 서비스에 필요한 최소한의 개인정보(아이디, 연동한 소셜 계정의 닉네임·프로필 사진)만 저장한다.
- 이미 정한 범위 밖 기능은 spec에 넣지 않는다. 필요해 보이면 열린 질문으로 남긴다.
- 에셋(캐릭터·배경·글꼴)은 상업적 이용이 허용된 것만 쓰고 출처를 남긴다.

**이유**: 3명 팀이 끝까지 완성할 수 있는 크기를 지킨다.

## 보안·무결성 기준

- 로그인 쿠키: `HttpOnly`, `SameSite=Lax`, 배포 환경에서는 `Secure`.
- 다른 사이트에서 보낸 요청(CSRF)은 거부한다(403).
- 비밀번호는 해시로만 저장하고 원문을 DB·로그·화면 어디에도 남기지 않는다.
- 로그인 유지: 기본은 브라우저를 닫거나 2시간 쓰지 않으면 로그아웃, [로그인 상태 유지]를 고르면 7일.
- 로그인 실패 메시지는 아이디 존재 여부를 알려주지 않는다.
- 응답 속도: 글 목록 화면은 1초 안에 보인다(배포 환경, 캐시 없는 첫 방문).

## 개발 흐름과 품질 관문

- spec 흐름: `/speckit-specify` → (필요하면 `/speckit-clarify`) → `/speckit-plan` → `/speckit-tasks` →
  `/speckit-implement`. spec은 영역별 하나(`specs/NNN-영역`)로 둔다.
- spec에는 무엇을, 왜만 적는다. 기술 스택, 파일 경로, 함수 이름 같은 구현 방식은 plan에 적는다.
- `main`에서 브랜치를 만들고 PR을 올린다. 다른 팀원 1명 이상이 승인하면 merge한다.
- merge 전에 타입 검사·린트·E2E를 통과한다. 자동 검사(CI)가 생기기 전까지는 PR 작성자가 직접 돌리고
  결과를 PR에 적는다.

## Governance

- 이 constitution은 spec, plan, task, 코드 리뷰보다 우선한다. 원칙과 어긋나는 설계는 plan의 복잡도
  정당화(Complexity Tracking)에 이유를 적어야 한다.
- 개정: PR로 올리고 팀원 1명 이상의 승인을 받는다. 개정 이유와 영향받는 spec을 PR 설명에 적는다.
- 버전: MAJOR(원칙 삭제·재정의), MINOR(원칙·섹션 추가나 크게 확장), PATCH(문구·오타).
- 모든 PR 리뷰는 원칙 IV(서버 권한)와 V(원장 무결성) 준수 여부를 확인한다.
